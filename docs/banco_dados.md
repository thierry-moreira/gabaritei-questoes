# Documentação Técnica: banco de dados do app do aluno (`banco_dados_aluno.py`)

## Descrição Geral
Este repositório contém apenas o **app do aluno**. O cliente Supabase do aluno é `banco_dados_aluno.py` — PostgreSQL via PostgREST com a **ANON key pública** e o **JWT do aluno**. O header legado `x-app-token` continua sendo enviado por compatibilidade, mas as policies atuais não o exigem (a função `eh_app_aluno()` foi removida pela migration `secure_global_writes`). O painel administrativo vive em um repositório privado separado (`gabaritei-admin`) e usa o próprio cliente com **service_role**, fora deste escopo.

| Módulo | Aplicação | Chave (`.env`) | Papel |
|---|---|---|---|
| `banco_dados_aluno.py` | App do aluno (`app.py` + Electron) | `SUPABASE_ANON_KEY` (**anon**) + JWT do aluno (header legado `APP_TOKEN`) | Pública por definição — protegida pelas policies RLS; escrita exige o dono (`auth.uid()`) |
| `banco_dados.py` (repo separado) | Painel administrativo (`app_admin.py`) | `SUPABASE_KEY` (**service_role**) | Bypass total de RLS — uso interno, jamais distribuído |

O módulo exporta a instância global `supabase` (mesmo nome usado nos patches `@patch('rotas.X.supabase')` e nos testes).

> [!CAUTION]
> **A `service_role` (`SUPABASE_KEY`) jamais pode ser embarcada no app do aluno/bundle Electron.** Ela dá bypass total de RLS — quem a extrair do binário teria acesso destrutivo ao banco. O app do aluno usa exclusivamente `banco_dados_aluno.py`.

## Políticas RLS (migrations `rls_policies_aluno` … `rls_owner_only_e_conteudo_publico`)
Todas as tabelas têm RLS habilitado. O desenho atual separa **dados do aluno (owner-only)** de **conteúdo público (views/RPC com colunas públicas)**. A migration `consolidar_rls_select_unico_dados_aluno` unificou o SELECT das tabelas de aluno; `rls_owner_only_e_conteudo_publico` (versionada em `docs/migrations/rls_owner_only_e_conteudo_publico.sql`) recria as policies, endurece grants e cria as views/função públicas.

- **Conteúdo** (13 tabelas: `questoes`, `alternativas_questao`, `textos_base`, `provas_origem`, `materias`, `topicos`, `subtopicos`, `orgaos`, `cargos`, `bancas`, `niveis_escolaridade`, `prompts_materias`, `legislacao_artigos`): **SELECT** para `anon`/`authenticated` — em `questoes`/`alternativas_questao` filtrado a `status='publicada'` (pendentes invisíveis fora do painel; migration `security_hardening_p1`).
- **Legislação (RAG leve)** (`legislacao_artigos` + RPC `buscar_legislacao`, migration `legislacao_busca`): **SELECT** para `anon`/`authenticated` — corpus curado de dispositivos legais que alimenta o grounding da `/api/ia_explica` (busca lexical FTS + filtro por matéria/tópico, sem embeddings). A ingestão é exclusiva do painel (service_role); a mesma migration cria `explicacoes_ia.contexto_legislacao` (jsonb — evidência dos trechos usados em cada geração; linhas antigas ficam `NULL`).
- **Cache IA** (`ia_cache_estudo`, `explicacoes_ia`): **SELECT** para `anon`/`authenticated`; a **escrita é exclusiva da Edge Function `secure-global-write`** (migration `secure_global_writes` revogou INSERT/UPDATE/DELETE diretos). A tabela de stats anônimas `historico_respostas_anonimo` é legado da era web — o app do aluno não insere mais, mas os dados históricos são preservados.
- **Feedbacks** (`feedbacks_questoes`): **sem grants nem policies para `anon`/`authenticated`**. A gravação passa pela Edge Function `secure-global-write` (operação `feedback_question`), que valida o JWT do aluno, o perfil, a questão publicada e o rate limit antes de inserir com `service_role`. Os relatos continuam anônimos (sem `id_usuario`). A triagem e a exclusão são exclusivas do painel/service.
- **Feedbacks de respostas da IA** (`feedbacks_ia`, migration `20261101_feedbacks_ia`): mesmo modelo dos feedbacks de questão — **sem grants nem policies para `anon`/`authenticated`**; gravação pela Edge Function `secure-global-write` (operação `feedback_ai`), com relatos anônimos sobre explicações/resumos/flashcards gerados. A triagem é humana, no painel admin (seção "Respostas da IA" da página de feedbacks), e a ação de invalidação de cache apaga linhas de `explicacoes_ia`/`ia_cache_estudo` pelo service_role para forçar a regeração.
- **Denúncias** (`reports_comentarios`, migration `reports_comentarios_denuncias`): **INSERT e DELETE apenas do dono** — `eh_dono_do_aluno(id_usuario)` (o `eh_app_aluno()` foi removido pela migration `secure_global_writes`); **sem SELECT para o app do aluno**. O endpoint grava com `returning=minimal` para não pedir `SELECT` nem expor a fila; a triagem é humana no painel admin, via `service_role` — seção "Denúncias de Comentários" da página de feedbacks, com exclusão do comentário denunciado ou descarte da denúncia. PK composta `(id_comentario, id_usuario)` impede denúncia duplicada (23505 → o app responde 409 amigável); FK `ON DELETE CASCADE` para `comentarios_questao` — comentário excluído no painel leva as denúncias junto. Substitui a antiga moderação por IA: a blocklist local (`utils.verificar_texto_improprio`) segue como primeira barreira na publicação.
- **Dados do aluno** (16 tabelas: `usuarios`, `historico_respostas`, `comentarios_questao`, `flashcards`, `flashcard_categorias`, `resumos_estudo`, `cadernos`, `caderno_questoes`, `filtros_salvos`, `simulados`, `simulados_questoes`, `simulados_resultados`, `editais_*`): **SELECT owner-only** — `(select auth.uid()) = auth_id` em `usuarios`; `eh_dono_do_aluno(id_usuario)` nas demais; `simulados` por `id_criador`; `simulados_questoes` pelo dono do simulado pai; `editais_*` por `id_usuario`. Sem JWT o papel `anon` recebe **200 com 0 linhas** (não 403), o que preserva o fluxo de restauração de sessão do `load_user`. **INSERT/UPDATE/DELETE exigem o JWT do dono** — a identidade é checada pelas mesmas expressões de SELECT acima. O header `x-app-token` e a função `eh_app_aluno()` foram removidos pela migration `secure_global_writes`; o cliente ainda envia o header por compatibilidade, mas ele não é mais consultado pelo RLS. A cláusula de legado em `usuarios` (`auth_id IS NULL` + e-mail do JWT) existe apenas para o 1º login pós-Auth e só alcança a própria linha.
- **Cadernos — vínculo e dono** (migration `caderno_questoes_dono_fk`): `caderno_questoes.id_usuario` é **NOT NULL** e a FK composta `(id_caderno, id_usuario) -> cadernos(id_caderno, id_usuario)` impede inserir/mover uma questão para caderno de outro aluno (`23503`), inclusive via `service_role`. As policies de INSERT/UPDATE também exigem `EXISTS` de um caderno do mesmo `id_usuario`; a rota `/api/cadernos/salvar` valida a posse antes do INSERT e devolve **404** para caderno alheio. Teste: `docs/migrations/test_f03.sql` (12 asserções).
- **Resultados de simulado — visibilidade do simulado** (migration `simulados_resultados_visibilidade`): as policies de INSERT/UPDATE de `simulados_resultados` exigem, além de `eh_dono_do_aluno(id_usuario)`, que o `id_simulado` esteja em `view_simulados_publicos` (público) **ou** em `simulados` com `eh_dono_do_aluno(id_criador)` (privado do próprio aluno). Assim, um aluno não grava/edita resultado em simulado privado alheio via PostgREST (falha `42501`), mesmo spoofando `id_usuario`. No app, o guard único `_simulado_do_usuario_ou_none` bloqueia fazer/corrigir/ranking/PDF antes de consultar questões ou gabarito. Teste: `docs/migrations/test_f04.sql` (13 asserções).
- **Comentários — formato e tamanho** (migration `comentarios_username_xss`): `usuarios.username` e `comentarios_questao.nome_usuario` têm CHECK de 2–30 caracteres na allowlist `[[:alnum:] ._-]` (`usuarios_username_formato` / `comentarios_nome_usuario_formato`); `comentarios_questao.texto_comentario` tem CHECK de 1–1000 caracteres, não vazio e sem caracteres de controle (`comentarios_texto_valido`). INSERT/UPDATE direto via PostgREST com HTML no nome, texto vazio/longo ou controle falha com `23514`, inclusive em nome denormalizado. O texto legítimo com `<`/`>` é permitido: a defesa contra XSS é a renderização com `textContent` no app (F-11). Teste: `docs/migrations/test_f11.sql` (8 asserções).
- **Conteúdo público separado dos dados do aluno** (migrations `rls_owner_only_e_conteudo_publico` + `security_invoker_views_publicas` + `ranking_simulado_private_wrapper`): `view_comentarios_publicos` (SELECT anon/authenticated; **sem `id_usuario`**), `view_simulados_publicos` e `view_simulados_questoes_publicas` (SELECT authenticated; somente `eh_privado=false`, **sem `id_criador`/e-mail**; `eh_meu` para a UI) e a RPC `ranking_simulado(uuid)` (authenticated; público para qualquer autenticado, privado apenas para o criador; retorna username + métricas, nunca `id_usuario`). Desde a migration `security_invoker_views_publicas` (lint 0010), a lógica privilegiada que ignora o RLS owner-only vive nas views `private.view_*` (`security_invoker=false`, schema não exposto na API) e os nomes em `public` são wrappers `security_invoker=true` com a mesma projeção. Desde `ranking_simulado_private_wrapper` (lint 0029), a RPC pública é um wrapper `SECURITY INVOKER` sobre `private.ranking_simulado`, que concentra a lógica `SECURITY DEFINER`. A segurança continua no filtro e nas colunas explícitas de cada uma. As rotas de comentários e de simulados do app usam essas projeções.
- **Feed público de comentários (F-07, sem migration adicional)**: `GET /api/comentarios/<id_questao>` consulta `view_comentarios_publicos`, pede somente `id_comentario`, `nome_usuario`, `texto_comentario` e `criado_em` e faz uma segunda projeção no servidor; nenhum `id_usuario` é serializado. A paginação entrega 20 itens por chamada (mais um registro interno como sentinela), ordena por `criado_em` + `id_comentario`, limita o offset a 10.000 e expõe `pagina`/`tem_mais`; o endpoint público aplica rate limit de 60/minuto por IP. A interface oferece carregamento das páginas anteriores.

**Camada de dono — Auth por usuário** (migrations `auth_usuario_e_policies` + `editais_leitura_por_dono` + `policies_para_authenticated`): cada aluno agora autentica no **Supabase Auth** (e-mail + senha) e `usuarios.auth_id` guarda o vínculo com `auth.users`. O SDK encadeia o JWT do usuário em todas as queries; como o JWT carrega `role=authenticated`, todas as policies foram regeneradas para `TO anon, authenticated`. Toda policy de escrita dos dados do aluno passou a exigir `eh_app_aluno() AND eh_dono_do_aluno(id_usuario)` (em `simulados` a coluna é `id_criador`; em `simulados_questoes` o dono é herdado do simulado); a migration `secure_global_writes` removeu o `eh_app_aluno()` e o header `x-app-token`, então hoje a escrita exige apenas a identidade do dono (`auth.uid() = auth_id` / `eh_dono_do_aluno(...)`) — resultado: mesmo que alguém extraia a anon key do binário, não escreve dados de outro aluno. O INSERT em `usuarios` usa `WITH CHECK (auth.uid() = auth_id)` (auto-cadastro da própria conta). As 3 tabelas de progresso de edital (`editais_materias`, `editais_topicos`, `editais_progresso`) ganharam `id_usuario` (FK CASCADE — eram herança do design single-user, sem dono) e leitura exclusiva do dono (não alimentam rankings). `feedbacks_questoes`, `feedbacks_ia`, `historico_respostas_anonimo`, `ia_cache_estudo` e `explicacoes_ia` não têm dono (são anônimas por design); as duas primeiras e os dois caches são gravados **somente** pela Edge Function `secure-global-write` — ver "Gravações globais" abaixo.

**Re-link de perfis legados** (migrations `relink_perfil_legado_usuarios` + `relink_visibilidade_select_legado` + `usuarios_update_policy_consolidada`): alunos das eras anteriores ao Supabase Auth ficaram com `auth_id = NULL`. No 1º login pós-Auth, o app tenta `UPDATE ... WHERE auth_id IS NULL` e o RLS só libera a linha quando o e-mail CONFIRMADO do JWT (`auth.jwt()->>'email'`, comparado com `lower()` dos dois lados) bate com o da linha. (O header `x-app-token` citado em migrations antigas foi removido por `secure_global_writes`.) Como o UPDATE do Postgres exige que a linha também seja visível às policies de SELECT, a policy `anon_le_dados_aluno` de `usuarios` ganhou a cláusula OR do legado (a própria linha, ainda sem vínculo, visível ao dono do e-mail do JWT). O UPDATE é liberado por uma **policy única**, `usuarios_update_proprio_ou_relink` (lint 0006): o `USING` aceita o próprio perfil ou a linha legada de mesmo e-mail e o `WITH CHECK` exige que o resultado fique vinculado ao `auth.uid()`. Isolamento verificado: tentar adotar a linha de outro e-mail afeta 0 linhas e ninguém troca o `auth_id` para terceiros.
- **`admins` e `logs_admin`**: **sem policies e `REVOKE ALL` de `anon`/`authenticated`** — deny-all de RLS + grant revogado (nem descobertas via GraphQL; qualquer acesso devolve `permission denied`).
- **Storage**: o bucket `imagens_questoes` é **público com public URLs diretas** no app (a policy SELECT de `storage.objects` foi removida — o signed URL de 60s não protegia nada num bucket público; migration `rls_header_app_aluno`). O **upload é exclusivo do painel** (`TO service_role`), com limite de 5MB e apenas mimes de imagem (png/jpeg/webp/gif).
- Todas as views expostas em `public` rodam com `security_invoker=on`: `view_questoes_completa` e `view_taxa_acerto_questoes` respeitam o RLS das tabelas base, e os wrappers `view_comentarios_publicos`, `view_simulados_publicos` e `view_simulados_questoes_publicas` delegam a lógica privilegiada às views `private.view_*` (migration `security_invoker_views_publicas`, lint 0010).

**Escrita dos dados do aluno** (migrations `auth_usuario_e_policies` + `secure_global_writes`): com o JWT do aluno encadeado pelo SDK, todas as policies de escrita exigem apenas a identidade do dono — `auth.uid() = auth_id` em `usuarios` e `eh_dono_do_aluno(id_usuario)` nas demais (em `simulados`, `id_criador`; em `simulados_questoes`, o dono do simulado pai). O antigo header `x-app-token`/`eh_app_aluno()` foi removido pela migration `secure_global_writes`; o cliente ainda o envia por compatibilidade, mas ele não participa mais do RLS. **A leitura das tabelas de dados de estudo é owner-only**: sem JWT, a anon key lê 0 linhas; o conteúdo público (comentários, simulados públicos e ranking) passa pelas views/RPC acima.

**Gravações globais** (migration `secure_global_writes` + Edge Function `secure-global-write`): feedbacks de questão/IA e caches de IA são escritas **globais e anônimas** (sem dono). Para impedir que a anon key embarcada seja usada para forjar relatos ou envenenar o cache coletivo, `anon`/`authenticated` perderam os grants de escrita nessas tabelas. O app do aluno envia a gravação ao backend Flask, que chama a Edge Function (`escrita_global.escrever_global`) com o **JWT do aluno**; a função (`verify_jwt: true`) valida o usuário no Supabase Auth, exige perfil em `usuarios`, confirma que a questão existe e está `publicada`, aplica rate limit por usuário e só então grava com `service_role`. Operações e limites por hora: `feedback_question`/`feedback_ai` (10), `cache_explanation` (20) e `cache_study` (30). Falha no cache **não** desfaz a explicação/resumo/flashcard já gerado — o aluno recebe o conteúdo e o cache é apenas ignorado. A função só aceita os campos exatos de cada operação (`validation.ts`), rejeita payloads fora do catálogo e responde códigos estáveis (`unauthorized`, `rate_limited`, `question_not_found`, `write_failed` etc.) que o Flask traduz em mensagens amigáveis.

Limites conhecidos (sem servidor, irreversíveis): o conteúdo é raspável por quem extrair a anon key; a leitura dos dados de estudo é **owner-only** (sem JWT: 0 linhas; entre alunos: cada um só vê as próprias linhas, com exceção do conteúdo público das views/RPC); quem extrair **a anon key + um JWT válido** ainda age como aquele aluno, mas não lê nem escreve em nome de outro `id_usuario`. A `service_role` continua fora do app.

**Hardening de grants** (migrations `security_hardening_p1` + `rls_owner_only_e_conteudo_publico`): além do RLS, `anon` e `authenticated` perderam `TRUNCATE` em todas as tabelas (RLS não se aplica a TRUNCATE; o PostgREST não expõe TRUNCATE), `anon` perdeu `INSERT/UPDATE/DELETE` nas 16 tabelas de dados do aluno (escrita sempre sai com JWT) e perdeu toda escrita nas 12 tabelas de conteúdo (só SELECT) e tudo em `admins`/`logs_admin` — defesa em profundidade contra qualquer regressão de policy. O `SELECT` de `anon` nas tabelas privadas foi mantido de propósito (retorna 0 linhas via RLS) para não transformar a restauração de sessão do `load_user` em `permission denied`.

**GraphQL desabilitado + advisor limpo** (migration `disable_graphql_move_trgm`): a extensão `pg_graphql` foi removida com CASCADE (o app nunca usou a API GraphQL; reversível com `create extension pg_graphql;`) e o `pg_trgm` foi movido do schema `public` para o `extensions` (o índice trinário de `textos_base` sobreviveu — índices referenciam a opclass por OID). Achados restantes do Security Advisor que são **design intencional**: `rls_enabled_no_policy` em `admins`/`logs_admin` (deny-all deliberado), o listing público do bucket `imagens_questoes` (as public URLs são usadas pelo app) e `auth_leaked_password_protection` (WARN de configuração do Auth — habilitar a proteção de senha vazada no dashboard). Os três `security_definer_view` foram eliminados pela migration `security_invoker_views_publicas` (lint 0010): em `public` ficaram wrappers `security_invoker=true` e a lógica privilegiada foi movida para `private.view_*`. O `authenticated_security_definer_function_executable` de `ranking_simulado` foi eliminado pela migration `ranking_simulado_private_wrapper` (lint 0029): em `public` ficou um wrapper `SECURITY INVOKER` e a lógica privilegiada foi movida para `private.ranking_simulado`. O `multiple_permissive_policies` de `usuarios` foi eliminado pela migration `usuarios_update_policy_consolidada` (lint 0006): as policies de UPDATE viraram `usuarios_update_proprio_ou_relink`. As policies de escrita atuais exigem apenas a identidade do dono (`auth.uid() = auth_id` / `eh_dono_do_aluno(...)`); o `eh_app_aluno()` e o header `x-app-token` foram removidos por `secure_global_writes`. Qualquer achado de policy permissiva deve ser reavaliado no dashboard. Chaves públicas: apenas a `anon` legacy permanece habilitada.

## Configurações de Rede (Resiliência de Conexão)
Para lidar de forma robusta com instabilidades de rede — incluindo oscilações de conexão com a internet típicas do uso local/desktop — o cliente Supabase é configurado explicitamente utilizando a classe `SyncClientOptions`:

- **Timeout do Cliente PostgREST**: Configurado para um limite estrito de 30 segundos (`postgrest_client_timeout=30`). Essa parametrização impede que requisições extremamente demoradas ou em gargalo de infraestrutura bloqueiem permanentemente as threads/workers síncronas do servidor Flask.
- **Cabeçalho de Conexão (Header Connection)**: Configurado como `"Connection": "close"`. Esta estratégia desativa o keep-alive do HTTP nas requisições da API do Supabase, evitando problemas crônicos de "Broken Pipe", vazamento de conexões abertas ou conexões em estado zumbi em proxies de infraestrutura que reciclam sessões de rede de forma intermitente.

## Variáveis de Ambiente e Trava Fail-Fast
O `banco_dados_aluno.py` depende de três variáveis no `.env` (ou no ambiente do processo spawnado pelo Electron):

1.  **`SUPABASE_URL`**: endpoint HTTP REST do projeto Supabase.
2.  **`SUPABASE_ANON_KEY`**: chave **anon** — pública por design, protegida pelas policies RLS.
3.  **`APP_TOKEN`**: segredo legado do app (gerado com `secrets.token_hex(32)`), ainda enviado em **todas as requisições ao PostgREST** no header `x-app-token`, mas **não exigido pelas policies atuais** — o `banco_dados_aluno.py` mantém o fail-fast e o header por compatibilidade até a limpeza do Electron/`.env`.

O app como um todo também usa **`FLASK_SECRET_KEY`** (sessão), **`GABARITEI_LOCAL_DIR`** (SQLite + DPAPI da chave BYOK; no Electron aponta para o `userData`) e, opcionalmente, **`TRUSTED_PROXIES`** (ProxyFix).

> [!CAUTION]
> **Mecanismo de Segurança Fail-Fast (Parada Imediata)**:
> Se `SUPABASE_URL` ou `SUPABASE_ANON_KEY` faltarem na importação, o módulo lança `ValueError` e interrompe a inicialização. O mesmo acontece se `APP_TOKEN` não estiver configurado — o cliente ainda exige a variável por compatibilidade, embora as policies atuais não usem o header. Isso evita subir a aplicação em estado inconsistente.

## Uso no Código
O módulo exporta a instância global `supabase` e os helpers de Auth:

```python
# Rotas do app do aluno (anon + JWT do aluno — protegida por RLS)
from banco_dados_aluno import supabase

# Auth (Supabase Auth): login, cadastro, refresh e reset de senha
from banco_dados_aluno import (
    entrar_com_senha, criar_conta_auth, restaurar_sessao,
    sessao_atual, sair_auth, pedir_reset_senha,
)

# Exemplo de busca de dados
resultado = supabase.table("usuarios").select("*").execute()
```

O cliente admin (`banco_dados.py`, service_role) **não existe neste repositório** — ele pertence ao repo privado `gabaritei-admin`.

## Práticas de Resiliência de Acesso a Dados
Embora a instância `supabase` esteja globalmente disponível, é considerada uma excelente prática **não invocá-la diretamente para escritas ou consultas cruciais em rotas**. 

Em vez disso, as operações devem ser empacotadas utilizando a função utilitária `safe_execute` localizada em `utils.py`. A função `safe_execute` adiciona uma camada de retentativa automática (até 3 tentativas, pausa fixa de `0.5` s e sem retry para erros determinísticos listados em `ERROS_SEM_RETRY`) para tolerar falhas pontuais e momentâneas de rede ou concorrência de requisições no Supabase.
